# 第27章 实战：规划—执行—检查的多智能体协作

> 读前回顾：[第10章](10-agent-task-modeling.md) · [第15章](15-marl-algorithms.md) · [第16章](16-team-credit-assignment.md) · [第17章](17-llm-multi-agent-training.md)

面对一个查询任务，规划者分解问题，执行者查数据，检查者核对口径。流程听起来合理，但三个人一起做，是否真比一个人做得更好？

这个案例把合作机制放进可比较的实验：先明确交接，再训练角色，最后用等预算对照和消融判断各自的价值。

## 27.1 定义角色、观测与交接

让三个角色共同回答合成数据库中的问题：规划者拆清实体、时间与统计口径，执行者调用只读工具，检查者对照证据核验。发现问题时，检查者返回具体待修复项，而不是自行改写工具结果。

例如用户询问“某类客户上一季度的平均交易额”。规划者首先明确客户集合、季度边界与平均方式，再把查询任务交给执行者；执行者返回查询与证据；检查者确认是否混淆客户平均与交易平均。这个例子使角色边界对应真实的信息处理步骤。

各角色应只获得职责所需内容。检查者需要需求与证据，不必读取隐藏答案；执行者需要可执行子任务，不应被要求猜测未表达的统计口径。信息边界清楚，才容易判断某次错误应由谁负责。

## 27.2 构建等预算对照

为了知道收益从哪里来，可以逐步增加学习：先用不训练的固定编排，再固定队友只训练一个角色，最后让共享模型按角色组织轨迹并联合更新。同时保留相同预算的单 Agent，统一总 token、工具调用与并发资源。

固定编排基线保留相同角色与消息协议，只不做策略更新。它用于测量“组织方式本身”的收益。仅训练执行者再与它比较，可判断工具行为改进是否已经足够；联合训练则进一步研究角色互动是否值得学习。

单 Agent 基线也应获得相近的总预算和工具能力。若多角色允许三倍调用，只能说明扩大系统资源可能有用，不能单独支持协作机制的结论。并发可减少等待，但也应报告总资源与尾部延迟。

## 27.3 奖励与角色贡献

团队终局奖励基于结果正确与证据一致，调用和通信记录为独立成本。角色反馈只奖励可验证子目标，先与纯终局反馈比较，避免同时引入多个未经验证的奖励项。

消融包括关闭角色间自由通信、取消检查角色、替换队友以及固定规划输出。若取消检查者后效果不变，需检查其实际贡献；若替换队友就退化，需研究共适应。最终报告成功率、成本、延迟及错误传播路径。

终局奖励可以根据结果与证据的一致性给出，再单独记录调用、通信和人工成本。最小版本先使用同一团队目标，避免同时引入复杂个体反馈，使收益无法归因。

如果需要过程奖励，可从明确可验的子目标开始，例如必要字段核验完成、发现可复现的口径冲突。不能只奖励“检查者提出问题”，否则检查者可能通过不断退回任务提高自己的得分。奖励设计应始终回到团队结果。

## 27.4 明确一次角色交接

规划者发给执行者的内容可限定为“目标、实体、时间范围、允许工具”；执行者返回“结果、证据引用、异常”；检查者返回“通过”或具体待修复项。这让每次通信都对应可检查的信息需求。

若三个角色都重新阅读全部原始材料、独立查询并长篇汇报，系统可能只是三次重复执行。先测量重复信息和调用，再判断是否需要学习通信或调整分工。

一次失败交接可以这样复盘：规划者写“查上季度”，执行者按最近三个月查询，检查者只验证 SQL 能运行。三者都完成了表面职责，团队仍错了。改进应先明确自然季度的边界和检查证据，再讨论训练谁。

消融还可分辨角色是否在实际使用信息。隐藏执行者的证据引用后检查结果不变，可能说明检查者只看文字风格；换一位执行者就大幅退化，则可能存在共适应。最终需要解释合作改变了哪些行为，而不只报告增加了几个角色。

下面是一条任务的最小交接示意。规划者确定“自然季度、逐客户求总额后取平均”，执行者据此生成查询并返回证据，检查者对照原需求检查时间与分母。若检查者发现使用了交易条数作分母，就返回这个具体冲突，执行者修复后再核验。

团队成功并不能说明三个角色都应获得同样解释。可固定规划输出，检查执行者能否完成；再固定正确执行结果，检查检查者是否会无故退回。角色测试与整体任务测试互相补充，能帮助区分基础能力不足与协作失败。
