# 第01章 强化学习解决什么问题

用户说：“帮我统计这类客户上季度的交易。”助手很快写出 SQL，却收到一条报错。接下来，是改语句、查表结构，还是先问清统计口径？答案能否做对，往往取决于这些看似不起眼的选择。

强化学习关心的，就是怎样从行动的结果中学会更好的选择。它把一连串决策放在一起，评价它们最终带来了什么。

## 1.1 从“给出答案”到“选择行动”

把这一过程展开，助手每做一次选择，就会得到新信息，也会消耗时间和预算。前一步的后果改变了后一步的处境，这就是**序列决策**。

强化学习把选择动作的方式称为**策略**。策略既可以是小型网络，也可以是生成工具调用的语言模型。学习目标是利用经历调整策略，使未来任务的期望累计回报更高。

| 解决方式 | 如何得到行为 | 适合的条件 |
| --- | --- | --- |
| 规则 | 人工规定情境与动作 | 情况可枚举，逻辑稳定 |
| 监督学习 | 模仿专家动作或答案 | 有足够且覆盖充分的示范 |
| 搜索与规划 | 比较候选路径的预期结果 | 环境模型可用，搜索成本可控 |
| 强化学习 | 用行动后的反馈更新策略 | 结果可评价，动作存在长期影响 |

这些方法可以组合：先模仿示范，再用搜索发现成功路径，最后用奖励改进策略。已知模型和约束下的调度问题，也应比较运筹优化方案。

这里有一个容易忽略的区别：策略描述的是“在什么情况下怎样选择”，某一次动作只是策略的一个结果。直接查询并不总是坏动作，先查结构也不总是好动作。熟悉的表、明确的口径与充足的预算，会使合理选择发生变化。因此，我们希望学到的是依赖情境的决策规律。

监督学习也能训练这样的规律，前提是有覆盖相应情境的示范。RL 的不同之处在于，训练信号可以来自整段经历的效果，而不必逐步指出标准动作。例如，专家不必标注每次报错后应该点击什么，但系统需要能够判定最终答案是否正确、总共花了多少资源。

## 1.2 为什么不能只看眼前奖励

如果只看当前一步，查看表结构似乎是在花钱；把后续报错也算进去，它却可能更划算。RL 用**累计回报**衡量这种跨步骤的取舍。

其中有三个基本困难：

- **延迟反馈：** 任务结束时才知道答案是否正确。
- **信用分配：** 最终成功后，需要判断哪些早期动作有帮助。
- **探索与利用：** 既要使用已知有效的行为，也要尝试尚未确定的选择。

例如，助手只重复“直接查询”，就永远收集不到“先查结构”这条路径的数据。策略改变行为，也改变下一轮训练看到的经历。这是 RL 与固定数据训练的重要差别。

奖励是对目标的可计算近似。若只奖励调用成功，助手可能反复执行无用查询；若只惩罚耗时，又可能过早结束。设计奖励前，应先写出独立的成功标准。

不妨作一个简化的计算。假设直接查询花1单位成本，以一半概率成功；失败后还需花3单位完成修复，且最终一定成功。那么总期望成本为 $1+0.5\times3=2.5$。若先查结构花1单位，随后查询再花1单位就一定成功，总成本为2。眼前多做一步，整体反而更省。

这是教学假设下的比较，真实成功率需要从数据估计。它说明了长期目标为何重要，却还没有解决学习问题：系统最初并不知道这些概率，也不知道哪种情境需要查结构。探索负责获得缺少的经历，信用分配负责利用经历改进早期选择；二者共同决定能否学到这种规律。

## 1.3 什么条件下值得采用 RL

把一个任务交给 RL 前，可以先顺着它走一遍：当前动作会不会影响后续？结果是否能判定？是否有足够经历可学？简单方案还有哪些不足？这四个问题，比先挑算法更能决定项目能否成立。

若只有一次预测、标签明确，监督学习通常是更直接的起点。若反馈极不可靠，或者每次探索都代价高昂，应先解决数据与环境问题。单步生成任务也可以用 RL 优化，只是长程决策不再是主要动机。

尤其要检查反馈是否能够区分“做得好”与“看起来忙”。若成功标准是给出正确统计结果，奖励却只累计工具调用次数，那么训练再稳定，也会朝错误方向优化。奖励需要容易计算，验收标准则需要忠于任务；二者可以有关联，但不应只剩同一个分数。

还要比较获得改进的代价。构建模拟环境、清洗轨迹、训练与维护策略都需要投入。若一条明确规则已经覆盖绝大多数失败，先采用规则通常更合算。RL 的价值应通过相同任务条件下的增量表现来证明，而不是由任务是否“足够智能”来决定。

## 1.4 执行、记忆与训练分别改变什么

| 变化 | 查询助手示例 | 改变的对象 |
| --- | --- | --- |
| 执行循环 | 报错后重新查询 | 当前任务状态 |
| 记忆更新 | 保存已知字段说明 | 后续可读取的信息 |
| 策略训练 | 用历史成败更新网络 | 选择动作的机制 |

一次反思可以改变当前回答；保存反思可以影响后续上下文；将反馈用于更新策略才形成学习过程。判断系统是否进行了 RL，要查看训练信号与更新过程，而不是仅看它是否能多轮工作。

例如，助手发现某张表的日期字段名有误，把纠正信息写入记忆。下一次它读到记忆后避开了同一错误，这是一种系统适应，却不意味着参数已经更新。若随后用这些经历做 SFT，学到的是示范行为；若依据任务回报学习不同动作的选择，则进入强化学习的讨论范围。

因此，分析一个所谓“会学习的 Agent”时，可以沿着三个问题检查：新信息存在哪里，什么对象接受了更新，更新信号是什么。这种分析并不否认记忆或规则的价值，而是帮助我们把系统效果归因到正确的机制。

先辨认哪些选择值得学习，接下来再把任务写清楚。下一章会用一个小迷宫，为状态、动作、奖励与价值建立共同语言。
