# 第13章 Agent 的学习闭环与持续改进

> 读前回顾：[第10章](10-agent-task-modeling.md) · [第11章](11-long-horizon-credit.md) · [第12章](12-agent-environments.md)

失败日志已经存了几万条，模型却没有自动变好。记录经历只是起点；接下来还得判断问题出在哪里，选择怎样的改动，再验证新版本是否真的改善。

Agent 的学习闭环，就是把一次次失败变成可检验的改进，而不是把所有问题都交给下一轮训练。

## 13.1 区分策略与运行系统

先把运行系统拆开看：Harness 组织工具执行、上下文、权限与日志；策略选择动作；工具把动作落实；记忆提供信息；评估器判断质量。任何一处修复都可能让任务表现变好，因此要知道这次进步究竟发生在哪里。

把系统拆开，是为了找到改进的实际入口。同一份失败日志，既可能提示需要补工具，也可能提示上下文过长、记忆检索错误或动作选择不当。只有最后一类已经被明确定位时，策略训练才有直接的改进对象。

还应固定一份可重建的系统配置。若提示、工具描述和模型同时变化，下一版表现更好也无法说明哪些认识值得保留。学习闭环应积累可解释的改进，而不只是积累版本数量。

## 13.2 从失败归因到干预

假如助手总因缺少字段说明而报错，最直接的改动是补好元数据接口。若说明已经存在，它却从不查看，可以补成功示范；若它知道该查什么，却总选错时机，再研究交互式训练。沿着失败找原因，通常比直接扩大训练更有效。

可以按失败发生的位置分组：未理解目标、选错动作、参数错误、工具执行异常、结果核验遗漏。每组再选典型案例人工回放。分类不必非常细，但应能导向不同干预，否则标签再多也难指导工作。

例如“结果错误”既可能来自 SQL 口径，也可能来自工具返回缺失。前者可以改善观测与决策，后者可能需要异常处理。把两者混成负奖励，会要求模型从不充分的输入中学出不存在的区分。

## 13.3 组织版本化学习闭环

一个可管理的闭环是：收集轨迹→分类失败→筛选与标注→提出单项改动→训练或调整系统→固定测试集评估→版本准入。新任务训练还应保留旧能力回归集，检查是否以遗忘原有行为换取局部提升。

离线定期更新通常更容易归因。若采用在线学习，需要进一步定义反馈延迟、标签纠正、更新频率和异常回退。评价闭环是否有效，应看新版本在独立任务中的质量、成本与恢复能力，而不是累计收集了多少轨迹。

轨迹进入训练前，至少要检查任务是否完整、标签是否可靠、行为版本是否可恢复，以及是否包含独立评估内容。成功轨迹也不能无条件保留：它可能碰巧猜中答案，或依赖已被撤销的工具行为。

更新后先回到同一批失败案例，判断目标错误是否减少；再评估未见任务和旧能力。第一步证明修复方向相关，第二步检验是否只记住案例。若只完成第一步，闭环可能演变成对固定错误清单的过拟合。

## 13.4 按失败原因选择更新方式

| 观察到的失败 | 先验证的改动 |
| --- | --- |
| 工具说明缺失 | 修复接口与上下文 |
| 忘记已知事实 | 调整检索与记忆 |
| 不会调用格式 | 增加示范或 SFT |
| 知道动作但时机不佳 | 比较规则、控制器与 RL |

例如，把工具错误描述改清楚后成功率上升，收益应归于接口改善。随后再比较训练前后策略，才能估计参数更新的增量。每轮都改提示、工具、奖励和模型，会使闭环难以积累可复用认识。

一个完整的改进假设应同时写出预期与代价。例如“加入结构检查动作后，字段相关错误减少，但调用数可能增加”。这样评估时既能看到质量收益，也能判断新增开销是否合理。

若新版本改善了目标错误，却引入过早求助，应继续分析奖励与动作空间，而不是只用总成功率掩盖变化。持续改进的单位可以是一次清楚的行为修复；多个这样的修复，才逐步形成可靠系统。

**例：从一次日期错误形成改进闭环。** 助手把“上季度”解释成“最近三个月”。回放后发现，工具中已有日历接口，但轨迹从未访问。团队可以先比较明确规则“相对时间先核验”与补充示范；若只有部分任务需要调用，再研究选择时机的策略。

训练或改动完成后，先在原错误类型中检查是否改正，再加入“本周”“上个自然月”和无需日期处理的任务。若新系统对所有问题都调用日历，错误虽少了，成本却可能不合理。这个闭环同时检验了修复效果与是否学会条件选择，而非仅记住某一道题。

单个 Agent 的闭环清楚之后，可以再加入第二个决策者。任务会多出分工与协作，也会多出“队友正在变化”这一学习难题。
