# 第30章 银行如何开展强化学习：从试点到能力建设

> 读前回顾：[第22章](22-experiment-design.md) · [第29章](29-why-bank-rl.md)

决定尝试一个方向后，很容易同时启动模型、平台、数据和多角色建设。几个月过去，系统越来越复杂，最初想改善的那个指标却仍说不清。

更稳妥的推进方式，是先让一个小任务形成完整闭环：有基线、有反馈、有独立评价，再凭证据扩大范围。

## 30.1 阶段交付与进入条件

| 阶段 | 最小交付 | 进入下一阶段的依据 |
| --- | --- | --- |
| 问题定义 | 一个任务、现有基线、指标与边界 | 业务能解释成功与失败 |
| 环境建设 | 快照、工具、标签、独立任务集 | 可重复执行并审计判定 |
| 最小训练 | 规则/模仿基线与单策略实验 | 等预算下出现稳定增量 |
| 鲁棒验证 | 留出场景、工具异常、消融与区间 | 收益不依赖单一模板或种子 |
| 影子试点 | 授权历史回放、建议与人工复核 | 真实分布下满足预设条件 |
| 受控使用 | 准入、监测、回退与责任安排 | 持续质量和成本证据成立 |

阶段之间的门槛应对应不同不确定性。问题定义解决“要改善什么”，环境建设解决“能否可靠评价”，最小训练解决“是否存在学习增量”，影子试点再检验“是否接近真实业务”。前一问题没有回答清楚，扩大后一阶段通常只会增加解释困难。

每阶段可保留一个简短结论：现有证据支持什么，尚不能支持什么，下一步怎样验证。它比用平台组件数量或模型规模衡量进度更贴近试点目的。

## 30.2 选择优化对象

先圈出真正要改的那一小块：是工具选择控制器、语言模型、调度器，还是多个角色的合作？只需改善工具路由时，可以从小型控制器开始。单主体尚未显示增量收益，增加角色也未必会让问题更清楚。

优化对象还决定数据需求。结构化控制器主要学习在有限动作中选择，语言模型则可能同时改变摘要与参数生成；联合训练又会改变角色接口。对象越多，一次失败的归因越难。

可采用逐步放开的设计：先冻结语言模型，训练工具时机；再研究参数生成；最后才考虑多角色联合更新。它不是唯一顺序，但能形成清楚的前序基线，帮助判断每次扩展是否值得。

## 30.3 数据与评价条件

数据侧分开管理业务快照、行为日志、示范、偏好和成熟结果标签。决策观测只能使用当时可获得的信息，评分器可以接触隐藏真值，但不能通过字段、报错或工具说明泄漏给策略。合成任务、授权历史回放与影子评估分别支持不同强度的结论。

业务快照需要保存“当时可见”的信息。最终调查标签可以在事后形成，用于评价动作；它不能通过客户摘要、文件名或工具错误悄悄进入策略输入。历史重放尤其容易把后来更新的资料误作当时已知。

反馈标注还应记录来源与成熟时间。专家初步建议、最终复核与模拟器真值具有不同含义，不能混成同一质量标签。建立少量有争议的案例集，有助于团队持续校准评价口径。

## 30.4 协作与验收

业务团队定义目标、证据要求和验收，算法团队负责策略与实验，数据平台负责快照、工具和轨迹，独立评估及相关管理团队审核适用范围。项目应共享一组具体失败案例，减少各团队对“成功”的不同理解。

通过条件须在测试前确定，例如在固定误报上限和人工预算下比较漏报、成本与尾部步骤；阈值应根据实际试点目标确定。

可以用同一份任务回放沟通：业务说明需要哪些证据，平台说明实际可用字段，算法解释为何选择该动作，评估方指出当前结论缺少什么对照。围绕具体轨迹，许多抽象争议会变得可检查。

验收也应同时看质量与行为变化。若策略成本下降，应核对是否减少了无用查询，还是省略了必要步骤；若转人工比例下降，应查看不确定样本的错误是否增加。单个总分很难承担这些判断。

## 30.5 最小试点的具体交付

可以先限定一个只读调查任务、一组工具、一个策略控制器和一个独立测试集。业务专家提供成功与失败判例，平台保存可重放快照，算法团队提交基线及训练对照，评估方根据事先确定的条件判断增量。

若该闭环不能重复得到可信结果，应先解决环境和评价；满足条件后，再扩大任务分布或尝试多主体。这样每次扩展都有可比较的前一阶段。

最小试点可以只覆盖一种任务模板，但要在模板内部保留主体、时间和参数变化，并设置独立留出。先证明环境与评分可靠，再要求学习稳定优于规则或模仿，不必同时追求复杂协作与对抗。

试点未通过时也应保留有用结论。例如发现多数失败来自缺失字段，就优先改善数据接口；发现规则已接近上限，就重新审视 RL 的增量空间。能够据证据停止或转向，同样是能力建设的一部分。
