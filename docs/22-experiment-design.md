# 第22章 从任务需求到实验方案

> 读前回顾：[第01章](01-why-rl.md) · [第02章](02-rl-foundations.md)

“我们准备训练一个更强的 Agent。”这句话能启动讨论，却还不能启动一场有结论的实验。更强是少犯错、少调用工具，还是更会处理异常？

把需求收敛为一个能比较、能验收的问题，往往是训练前最重要的一步。

## 22.1 把目标写成可验收的问题

把开头的愿望改写成一句可检验的话：“在结果正确率满足预设门槛的条件下，减少只读问数任务的工具成本，并降低超时比例。”现在我们知道要看什么，也能据此确定动作、环境和验收集。

一个目标至少要明确任务分布、质量口径和成本口径。只说提高成功率，可能通过增加重试获得；只说减少调用，可能通过全部转人工实现。把这些指标同时写清楚，才能排除显然不符合业务意图的捷径。

例如问数实验限定只读查询，成功需要实体、时间和统计口径全部正确，转人工单独报告。这样，一个很会停止却从不回答的策略，不会因为省调用就被误认为整体更好。

## 22.2 固定实验条件

训练前，把任务、用户价值、观测与动作、结束条件、反馈来源及延迟写在同一页上，再补齐基线、训练对象、数据划分、预算和通过条件。写不清的地方，通常也是实验开始后最容易产生争议的地方。

数据划分应在生成与采样前考虑。相同模板只替换客户名，通常不算独立的新问题；同一实体不同时间的任务，也可能共享大量证据。按实体、时间和模板隔离，分别检验不同类型的泛化。

基线也需要公平投入。固定规则、示范模型、未训练控制器各自代表不同起点。复杂训练若只胜过随机策略，只能说明学到了一些东西，尚不能说明比已有简单方法更值得部署。

**例：把问数项目填写成实验。** 任务来源限定为合成只读查询，按实体、时间和生成模板划分训练与测试；冻结模型与工具，只训练选择查询、核验和停止的小型控制器。基线为固定顺序与基于错误类型的规则策略。

主要指标为任务正确率与工具成本，转人工和超时单列。先在独立验证集选择配置，最终测试只作验收；训练预算同时计入成功与失败轨迹。若成本下降却遗漏必要核验，或改进只出现在已见模板，就不支持原来的项目假设。

写到这一步，算法还未确定，实验却已经有了可以讨论的对象。后续选择 PPO 或其他方法，是在这个问题定义内作技术取舍。

## 22.3 从最小闭环开始

先验证环境与评分器：合法动作是否被执行，错误是否可定位，成功是否真的改变目标状态，标签是否泄漏。再用少量任务检查采样、优势与参数更新链路。若策略连简单任务都不能改善，应先排查环境和梯度，而不是直接扩大训练。

预算要同时覆盖数据生成、失败重试、奖励计算、训练和评估。预先设定停止条件，例如达到预算、连续若干轮验证无改善或关键约束退化，避免只展示耗费大量尝试后最好的检查点。

最小闭环可用一个确定性任务开始：人工已知正确动作顺序，奖励能明确区分成功与失败，工具无外部变化。先确认轨迹完整、优势有差异、参数确实更新，再逐步增加任务随机性与规模。

这类检查不能证明泛化，却能缩小故障范围。如果连已知可完成的小任务都没有改善，先检查奖励符号、结束掩码、行为概率和梯度；直接扩大数据，可能只会让同一个错误运行得更久。

## 22.4 将项目写成一个假设

可以写成：“在固定任务集和相同调用上限下，训练工具控制器能减少重复查询，同时保持结果质量。”它明确了对象、对照条件和预期行为变化。

验证时先固定工具、提示和评分器，仅改变控制器。若无收益，再检查动作空间、数据或算法；若同时更换数据库、模型和奖励，实验无法回答原假设。

假设也要写出可否证的情形。比如期望通过减少重复查询降低成本，那么评估除了总调用数，还要统计相同参数重试比例。若调用变少只是因为更早放弃，原假设并未获得支持。

实验结束后可以按“观察—解释—限制”记录：观察到哪些指标变化，哪些轨迹支持机制解释，哪些任务或预算没有覆盖。一次没有正收益的实验，只要清楚排除了某条假设，同样可以指导下一步。
