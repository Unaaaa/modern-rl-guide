# 第25章 部署与持续迭代

> 读前回顾：[第21章](21-safe-and-robust-rl.md) · [第24章](24-evaluation-and-debugging.md)

实验通过了，但把模型权重换上去，并不一定能复现实验表现。角色提示、工具接口、预算，甚至队友版本，都可能改变它接下来采取的动作。

部署要交付的是一套能够重建、观察和回退的行为。模型只是其中一部分。

## 25.1 管理一组兼容版本

设想只升级了检查者，它开始要求更多证据，规划者便不得不改变后续安排。即使其他权重未动，整套系统的行为也已变化。因此，一次发布应绑定策略、角色提示、工具定义、环境适配、评分器和预算，多角色系统还需记录相容的队友组合。

可把发布清单理解为恢复某次行为所需的全部条件：权重、提示模板、工具 schema、记忆或检索配置、预算、角色映射及相关服务版本。并非所有项目都需同样复杂，但清单应足以解释任务为何这样执行。

多角色还需记录兼容组合。一个更严格的检查者可能适合新版执行者，却与旧执行者反复争执。单模型指标不能替代整套流程回归。

## 25.2 准入、监测与回退

先做冻结任务回归，再在影子模式生成建议，随后按项目边界开展有限验证。准入指标应包含质量、成本、异常与人工介入；异常时回退到已验证策略或既有流程，并保留当时观测和动作记录。

影子模式让新策略在相同输入上生成建议，而不直接承担正式动作，可以收集分歧与成本证据。它不能完整证明真实执行后果，因为建议尚未改变环境；仍需明确哪些结论来自回放，哪些需要进一步验证。

回退条件也应尽量具体，例如工具异常率、关键错误类型或尾部耗时触发阈值时，恢复已验证组合并保留轨迹。阈值取决于项目目标，关键是事先定义，避免在退化发生后临时改变口径。

**例：一项工具接口变化。** 查询工具新增了必填时间字段，旧策略仍按原参数调用。此时失败率上升，原因并非策略突然遗忘，而是部署接口不再兼容。先固定旧接口回放，再验证新适配，可以迅速区分接口问题与决策问题。

若发布包没有记录工具 schema，这类变化可能被误判为模型退化；若立即用报错轨迹再训练，又可能掩盖真正原因。版本记录与回退的作用，正在于让修复优先发生在产生问题的那一层。

## 25.3 持续迭代与标签延迟

反馈可能延迟，生产分布也会变化。应把暂缺标签与确定失败区分记录，待标签成熟后更新评估。遇到新问题，先判断是工具、知识、任务分布还是决策策略变化，再决定修复流程、补充数据或重新训练。

持续学习不要求每个生产反馈都立即触发参数更新。按版本积累数据、离线更新、独立评估后发布，通常更便于定位收益和退化来源。

反馈延迟时，可以分别保存当前状态、暂定标签和成熟标签。迟到结果可能纠正原来的判断，训练数据因而需要可追踪的标签版本。把尚未得到结果的任务当作失败，会使长周期任务受到系统性惩罚。

漂移也需要定位来源。用户问题变了、工具字段变了、评分标准变了，分别要求不同处理。仅发现成功率下降便立即再训练，可能把接口错误进一步写入策略。

## 25.4 一次可定位的回退

假设新检查角色使平均正确率提高，却频繁把任务退回执行者，导致尾部耗时越界。应能按完整版本组合回退，并回放新增轮次，判断问题来自检查标准、交接逻辑还是策略本身。

只恢复某个模型权重，却保留不兼容的角色提示与工具 schema，可能无法恢复原行为。因此部署单元应包含完整可重建配置。

回退完成后，应对引发问题的任务作有针对性的复盘。先固定权重只换提示，再固定提示比较工具版本，必要时逐项恢复，寻找最小触发条件。完整版本管理为这种比较提供基础。

修复之后，既要验证目标故障消失，也要检查原来改善的质量是否保留。持续迭代因此形成一个循环：发现问题、提出机制解释、进行有限改动、独立验证，再进入下一版本。部署后的经验只有经过这一过程，才真正变成可管理的学习材料。
